HKFC Foobtall Odds Prediction Model

Project Goals and Objectives

A machine learning pipeline that predicts HKJC (Hong Kong Jockey Club) football betting odds (Home/Draw/Away, 1X2) for upcoming matches. The model compares predicted odds against HKJC’s published odds to identify potential value bets.

It takes everything knowable about a football match before it is played – team strength, recent form, squad injuries, news sentiment, and historical odds – and predicts what the Home / Draw / Away (1X2) betting odds for that match should be. Those predicted odds are then compared against the odds that HKJC actually publishes. If the model thinks a team is more likely to win than HKJC’s odds imply, that is flagged as a potential value bet.

  • Inputs (features): Team ratings, recent results, squad injury reports, news headlines, published HKJC odds, handicap lines, pool liquidity, line movement between fetch snapshots, and (new in v4) API-Football pre-match win probability predictions.
  • Outputs (targets): Three decimal odds – odds_home, odds_draw, odds_away.

Why predict odds and not just the winner? Odds encode probability and the bookmaker’s margin in one number. Predicting odds directly is richer than predicting a binary win/loss outcome, because it lets you measure by how much you disagree with the market and whether that disagreement is large enough to act on.

Process and Approach

  • Initially begin with acquisition of Elo rankings data, initial acquisition of HKJC football match data from [hkjc-api](https://github.com/Bobosky2005/hkjc-api) repository, and investigations on acquired JSON data, how data is formatted and can be stored; Elo rankings data regularly updated.
  • Selected multioutput regression as machine learning method of focus for prediction of odds for home team victory, away team victory, or draw.
    • Given how the sum of reciprocals of odds must sum up to approximately 1 (+ bookmaker margin), odds_away, odds_draw, odds_home are assumed to not be entirely independent from one another; regardless, both direct multioutput regression (MultiOutputRegressor()) and chained multioutput regression (RegressorChain()) are tested, with chained multioutput regression optimised for ordering of chain.
    • Categorical feature types: venue_code, tournament_frontEndId, tournament_nameProfileId, tournament_code
    • Enforced “sum of reciprocals of odds must sum up to approximately 1 (+ bookmaker margin)” with ConstrainedOddsWrapper() class.

Data Storage

  • All data acquired is saved and stored on Google Cloud as .parquet files to minimise storage space.

HKJC Data Layer

  • HKJC data layer used as source of truth to acquire data that can be accessed with fetch_hkjc_match_details.py in conjunction with [hkjc-api](https://github.com/Bobosky2005/hkjc-api) repository; limited to matches in near future. fetch_hkjc_match_details.py specifically discovers current HKJC matches, fetches full details for each, saves the results locally, and uploads them to Google Cloud Services.
  • Integration paths:
    • Path A – Node.js bridge (--hkjc-source api, bridge method): The hkjc-api npm package wraps HKJC’s internal GraphQL API. Requires Node.js and a Hong Kong IP address.
    • Path B – Direct HTTP (--hkjc-source api, httpx method): Uses Python’s httpx library to call the same HKJC endpoint directly. Also requires HK IP. Currently unreliable in practice.
    • Path C – Local Parquet (--hkjc-source parquet, default): Loads data/hkjc/df_hkjc.parquet. No network calls, no IP restriction.
    • Path D – Fetch Parquets (--hkjc-source fetch): Loads all matchDetail_*.parquet files from data/hkjc/ produced by fetch_hkjc_match_details.py. Richer than Path C because it includes additional columns and computes line movement between snapshots. Additional columns from Path D (fetch only).

API-Football Enrichment Layer

  • API-Football fills the gaps in data from HKJC data with team form, squad availability, H2H history, league standings, and a pre-match win probability model. It runs alongside SportsAPIPro as a parallel enrichment option – both write to separate parquet files and the pipeline selects between them via --sp-parquet.
  • Two-layer design of enrichment system:
apif_incremental_fetch.py  (orchestration layer)
  |-- Loads HKJC parquet(s)
  |-- Builds coverage index from existing APIF parquet
  |-- Identifies uncovered matches
  |-- Batches calls to client
  |-- Merges and deduplicates results
  |-- Saves output parquet + caches
  |-- Uploads to GCS
  |
  +-- APIFootballClient  (HTTP layer, api_football_client.py)
        |-- Rate limiting (10 req/min, 6s between requests)
        |-- Daily quota tracking (soft cap at daily_limit)
        |-- Exponential backoff on 429 (10s, 20s, 40s, 80s)
        |-- Team ID cache (persistent JSON)
        |-- No-result log (avoids re-querying known failures)
        |
        +-- v3.football.api-sports.io
              /teams  /fixtures  /fixtures/headtohead
              /players/squads  /injuries
              /predictions  /odds  /standings
  • api_football_client.py is a pure library file never run directly. All HTTP calls go through a single _get(endpoint, params) method that handles four concerns:
    • Rate limiting: Enforces the 6-second inter-request gap unconditionally. No time.sleep() calls needed in endpoint functions.
    • Daily quota tracking: _daily_used is incremented on every successful response. When it reaches daily_limit, all subsequent calls return {} without hitting the API. A quota warning is logged at 90% of the limit.
    • 429 handling: Retries with exponential backoff – 10s, 20s, 40s, 80s. If all four retries fail, returns {} and the match is skipped cleanly.
    • Error isolation: All HTTP errors are caught and converted to {}. A failed call for one match never aborts enrichment of subsequent matches.
Team ID resolution
  • HKJC provides English team names; API-Football uses integer IDs. resolve_team_id() translates via /teams?search=:
    • Pass 1 – exact case-insensitive match. Covers the majority of well-known club names.
    • Pass 2 – country hint filter. If provided by the caller, filters results by country (e.g. "England"). Not populated automatically by enrich_match() but available for manual overrides.
    • Pass 3 – fuzzy best match. rapidfuzz token_sort_ratio ≥ 70 across all candidate names. Handles variations like "Atletico Madrid" vs "Atletico de Madrid".
  • Output: data/sportsapipro/apif_enrichment.parquet. Column names mirror sportsapipro_data_odds.parquet so --sp-parquet is the only change needed in the pipeline.

Incremental fetch script – apif_incremental_fetch.py

Four steps on every run: - Step 1 – Build coverage index. Reads existing apif_enrichment.parquet and builds (home_norm, away_norm) lookup dict. HKJC matches with fuzzy score ≥ 80 against any key are considered covered and skipped. - Step 2 – Identify uncovered matches. find_uncovered_matches() uses exact then fuzzy matching, returning only rows that fail both. Matches already in apif_no_result_matches.json are also skipped before any API call. - Step 3 – Batched API calls. Uncovered matches are grouped into batches of batch_size (default 8). Before each batch the quota is checked – if fewer than ~9 requests remain, the run stops cleanly at a batch boundary. batch_sleep (default 5s) is a safety margin above the per-request rate limiting inside _get(). - Step 4 – Merge and save. New rows are concatenated with existing parquet and deduplicated on (home_name_normalised, away_name_normalised, match_date) with keep="last". Sorted by match_date, saved as snappy-compressed parquet, caches written to disk, parquet uploaded to GCS.

API-Football Evaluation Script

  • api_football_evaluate.py is a standalone coverage evaluator that runs against the HKJC parquet before committing to a full incremental fetch. It samples N matches, attempts full enrichment for each within a configurable request budget, and produces a JSON coverage report with aggregate metrics.
  • The API-Football coverage for HKJC matches – particularly for Women’s leagues, Asian regional competitions, and international friendlies – is not guaranteed. The evaluation script validates coverage rates before spending the daily API quota on a full fetch run.
Metric What it measures

h2h_coverage Fraction with H2H history available

NLP / Sentiment Layer

  • Reads recent news headlines, scores sentiment, and produces model features. Only active when SP_SOURCE = "api". spacy/nltk imports are wrapped in try/except due to typer/click version conflicts; _NLP_AVAILABLE flag controls whether sentiment features are computed.

  • n_pools and has_fgs are in NUMERIC_COLS. The five apif_pred_* columns are commented out in NUMERIC_COLS – uncomment them in football_hkjc_ml_pipeline_v3.py S6 to activate them as model features when using apif_enrichment.parquet.

Model Architecture

  • RegressorChain (default): Predicts in sequence: home odds first, then draw using home as input, then away using both. Forces the model to respect the overround constraint (1/home + 1/draw + 1/away ≈ 1.10).
  • Key hyperparameters: iterations=900, learning_rate=0.04, depth=6, l2_leaf_reg=3.0, random_seed=42.

Volume & Sample Weights

  • Weights training rows by recency, team frequency, and market liquidity.
w = recency_weight * frequency_weight * liquidity_weight

recency    = exp(-ln(2) * days_ago / 180)   # 180-day half-life
frequency  ∝ abs(home_win_rate - 0.5) + abs(away_win_rate - 0.5)
liquidity  ∝ 1 / overround

Training Pipeline

  • Orchestrates the full training process. GCS sync before loading data and GCS upload of results after training.
  • At the start of training, sync_down() pulls from GCS:
hkjc/fetched/  -> data/hkjc/
hkjc/training/ -> data/hkjc/
sportsapipro/  -> data/sportsapipro/

After training: mlruns/ synced to GCS; JSON training summary saved to results/train/.

Evaluation and Future Improvements

  • Limitations on [hkjc-api](https://github.com/Bobosky2005/hkjc-api) mean HKJC historical and significantly further future data cannot be acquired; difficult to backtest or test on unseen data, and generally difficult to acquire HKJC data to begn with.
  • Difficult to acquire football odds data; the most reliable source of football betting odds, Opta data, is strictly locked behind an enterprise-level B2B paywall and is not available via public, open-access, or low-cost hobbyist tiers, and other providers found are of questionable credibility and/or far too costly for a smaller project.
  • Questionable if prior betting odds and corresponding match information would even be sufficient for predicting future football betting odds, or are even in the right direction for such.
  • Could be more beneficial to acquire movement data within each match and utilise a machine learning method that could account for such.
